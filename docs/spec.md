## 3. Решения

Заданы границы и контракты. Архитектуру, разбиение на модули и порядок работы выбирает исполнитель.

### 3.1 Стек

- TypeScript, Node.js 22, grammY.
- PostgreSQL.
- Клиент Jev: официальный `@typesafe-ai/sdk` или прямой HTTP к `POST https://api.typesafe.ai/v1/systemone`. Суммарное число попыток одной оценки, включая встроенные повторы SDK, не больше трёх.
- Mini App: выбор исполнителя. Бюджет: сумма размеров HTML, CSS и JavaScript до первого интерактивного состояния не больше 150 КиБ при сжатии Brotli. Проверяется командой на production-сборке, которая падает при превышении. Изображения и Telegram SDK в бюджет не входят.
- Поставка: `docker-compose.yml`, сервисы `bot`, `web`, `db`; образы собираются под `linux/arm64`.
- Веб слушает локальный порт по HTTP. HTTPS даёт внешний Caddy, в задачу не входит.

### 3.2 Границы наружу

| Граница | Настройка |
|---|---|
| Telegram Bot API | `TELEGRAM_BOT_TOKEN`; long polling; `allowed_updates`: `message`, `edited_message`, `message_reaction`, `message_reaction_count`, `chat_member`, `my_chat_member`, `callback_query`, `chat_join_request` |
| Jev | `TYPESAFE_API_KEY`; модель `jev-1.13.0`, алиасы запрещены |
| Модель описания | OpenAI-совместимый endpoint: `VISION_BASE_URL`, `VISION_MODEL`, `VISION_API_KEY`; без ключа медиа не описывается, остальное работает |

Каждая граница закрыта интерфейсом с управляемым двойником для тестов. Двойник допустим только на этих трёх границах. База в тестах настоящая. Источник времени и источник случайности передаются явно.

### 3.3 Ключи данных

- Каждая доменная запись содержит `chat_id`.
- Участник чата уникален по `(chat_id, user_id)`.
- Сообщение уникально по `(chat_id, message_id)`.
- Именная реакция уникальна по `(chat_id, message_id, actor_kind, actor_id, reaction_type)`, где `actor_kind` - `user` или `chat`.
- Снимок анонимных реакций уникален по `(chat_id, message_id, reaction_type)`.
- Настройка уникальна по `(chat_id, key, version)`.
- `chat_id` для запросов Mini App берётся только из проверенного контекста, раздел 3.8.

### 3.4 Карма

Карма - сумма событий журнала. Каждое событие хранит причину, источник, ссылку на сообщение и ключ идемпотентности. Кэш текущего значения пишется одной транзакцией с событием. Значения хранятся как `numeric(12,4)`, округление только при отображении.

Реакция участника A на сообщение участника B:

```
delta = base × message_factor(k_message) × pair_factor(k_pair) × voter_weight(karma_A)
message_factor(k) = 1 / (1 + ln(k))
pair_factor(k)    = 1 / (1 + ln(k))
voter_weight(x)   = 1 + ln(1 + max(0, x) / K)
```

`k_message` - порядковый номер реакции под этим сообщением, `k_pair` - порядковый номер реакции от A к B за последние 30 суток; оба начинаются с 1. Для минусующей реакции `base` отрицательный, формула та же.

Реакции Telegram:
- `message_reaction`: считается разность множеств `new_reaction − old_reaction` и `old_reaction − new_reaction`; каждая добавленная и снятая реакция обрабатывается отдельно.
- `message_reaction_count`: хранится последний снимок количества по типу; начисляется или отменяется только разность со снимком, без `pair_factor` и `voter_weight`. Снимок и события пишутся одной транзакцией. Обновление с `date` меньше сохранённого игнорируется.

Сигналы лестницы:
- Ответ определяется `reply_to_message`.
- Цитата - ответ с полем `quote`.
- Диалог - автор исходного сообщения ответил на прямой ответ другого участника в той же цепочке не позднее 24 часов (решение лида).
- Благодарность - ответ с `is_thanks` не ниже порога.
- На одну связь двух сообщений действует только самый дорогой подтверждённый сигнал. Более дорогой заменяет дешёвый: компенсирующее событие и новое начисление.
- Ответ, у которого `rude` не ниже порога при тоне `serious`, сигналов ответа и диалога не даёт.
- Стикер или гифка в прямом ответе, которые Jev признал уместными (`media_fits` не ниже порога), дают сигнал «реакция». Без описания медиа сигнал не начисляется.
- Серия сообщений одного автора подряд: начисление Jev за k-е сообщение подряд умножается на `1 / (1 + ln(k))`.

Убывание: за каждый полный период `30 × 24 часа` неактивности после срока тишины

```
new = max(lower_bound, old − 0.10 × abs(old))
```

Серия: активная неделя - неделя ISO в часовом поясе чата (настройка `timezone`, по умолчанию `Asia/Tashkent`), в которой есть хотя бы одно сообщение участника с `is_flood` ниже порога. Серия растёт при смежных активных неделях и обнуляется после первой пропущенной. Надбавка умножает положительные начисления.

Плановые задачи идемпотентны по ключу (задача, период, участник или чат).

Значения по умолчанию:

| Параметр | Значение |
|---|---|
| Реакция, `base` | 1 |
| Ответ | 2 |
| Цитата | 3 |
| Диалог | 4 |
| Благодарность | 6 |
| Минусующая реакция, `base` | -1 |
| Подтверждённая жалоба | -20 автору, +5 заявителю |
| Оценка пользы Jev, уровни 0-4 | 0, 0, 0.1, 0.25, 0.5 |
| K | 100 |
| Дневной лимит минусующих реакций от участника | 5 |
| Минимальная карма для минусующей реакции | 1 |
| Нижняя граница кармы | -50 |

Инвариант значений по умолчанию: наибольшее начисление Jev за сообщение строго меньше первой положительной реакции человека. Проверяется тестом.

### 3.5 Вопросы к Jev

Нормативная схема - `eval/questions.json`. Состав вопросов, типы и ключи - часть контракта и проверяются тестом на проводе. Вопросы хранятся в настройках чата, стартовое значение берётся из файла.

`state` - объект с полями `message`, `replied_to`, `previous_messages`, `media_description`, `sender_profile`. Отсутствующее поле передаётся как `null`. Текст участника передаётся только в `state`; в `instructions` и `criteria` он не подставляется.

Итог по спаму считает код: `spam = max(spam_earnings_crypto, spam_topic_pivot, spam_channel_bait, spam_other_offer)`. Категория записи бани - имя вопроса с наибольшим значением; для профиля - `profile_promo`.

Вопрос `profile_promo` задаётся только при наличии данных профиля, `media_fits` - только при наличии `media_description` и `replied_to`.

Размер запроса: до вызова оценивается весь JSON. Соблюдаются оба лимита: 64k токенов на запрос и 32k на `state` плюс самый длинный вопрос; оценка токенов - число знаков, делённое на 2. Порядок усечения: старые `previous_messages`, `replied_to`, `media_description`, `sender_profile`, затем `message` с пометкой об усечении. Если наименьший запрос не помещается, вызов не выполняется, в журнал пишется `context_too_large`.

Пороги по умолчанию: `is_thanks` 0.5, `is_answer` 0.5, `is_question` 0.5, `is_flood` 0.5, `media_fits` 0.5, `rude` 0.8. Предыдущих реплик в `state`: 3. Порог реакции бота: уровень пользы 4 при уверенности не ниже 0.7.

### 3.6 Спам, баня, наблюдение

Первое учитываемое сообщение - первое полученное ботом `message` участника в данном чате. Импорт истории этот номер не меняет. Повторная доставка и редакция нового сообщения не создают.

Правила применяются сверху вниз, первое подошедшее прекращает разбор:

| № | Условие | Действие |
|---|---|---|
| 1 | чат в режиме наблюдения | карточка админам «сделал бы: …», больше ничего |
| 2 | карма участника ≥ `protect_threshold` и (`spam` ≥ `spam_review_threshold` или `profile_promo` ≥ `profile_auto_threshold`) | карточка админам |
| 3 | первое учитываемое сообщение и (`spam` ≥ `spam_auto_threshold` или `profile_promo` ≥ `profile_auto_threshold`) | парилка |
| 4 | `spam` ≥ `spam_review_delete_threshold` | удалить сообщение, карточка админам |
| 5 | `spam` ≥ `spam_review_threshold` | карточка админам, сообщение остаётся |
| 6 | иначе | ничего |

Пороги по умолчанию: `spam_auto_threshold` 0.60 (решение владельца 29.10: от 60% бот сам удаляет сообщение и отправляет автора в парилку; сохранённые значения выше 0.60 миграция 014 опустила до 0.60), `profile_auto_threshold` 0.80, `spam_review_delete_threshold` 0.50, `spam_review_threshold` 0.30, `protect_threshold` 100. Решение лида. Прогон `research/09` - проверка работоспособности, а не калибровка: размеченного набора спама нет. Калибровка порогов выполняется лидом в неделю наблюдения и в задачу исполнителя не входит.

Режим наблюдения: при первом подключении бота к чату сервер сохраняет `observation_started_at`. До `observation_started_at + 7 × 24 часа` чат в режиме наблюдения. Состояние переживает перезапуск. Импорт истории начало не сдвигает. Досрочного отключения нет. Админ может продлить режим настройкой `observation_until`.

Парилка, бан и разбан - сохраняемый автомат состояний с идемпотентными шагами. Telegram и PostgreSQL общей транзакции не образуют: перед внешним вызовом сохраняется намерение, после успеха - результат; повтор продолжает с первого незавершённого шага. Состояние «завершено» ставится после всех обязательных шагов.

Шаги парилки: удалить сообщение, ограничить участника, создать запись бани, отправить реплику. Срок парилки 24 часа. Испытательный срок после разбана: 5 сообщений, ссылки запрещены, `spam_review_delete_threshold` для участника 0.30.

Разбан (решение владельца 29.10): кнопка «Разбанить меня» во вкладке «Разбан» снимает автоматическое наказание сразу, без объяснения и без Jev. Одно нажатие на запись бани, только после первой бани; дальше испытательный срок. Если админ оставил наказание в силе, кнопки нет. Кнопка ждёт, пока завершатся бан по сроку парилки и действие админа над тем же участником; пока идёт разбан, админ получает «Уже выполняю предыдущее решение». Запись, которую админ взял на себя или оставил кнопкой «Забанить», кнопка не трогает (модель `specs/tla/Appeal.tla`).

Редакцией считается только обновление `edited_message`, в котором изменилось содержимое: текст, подпись или вложение. Telegram присылает `edited_message` и при смене тега отправителя (`sender_tag`); такое обновление ничего не меняет и оценку не запускает (факт 29.09: расстановка 201 тега вызвала 904 повторные оценки старых сообщений и 58 карточек). Для сравнения хранится хэш содержимого, не текст. Если хэша у сообщения ещё нет, первое такое обновление только сохраняет хэш.

Редакция сообщения заменяет только оценку и событие Jev. Выполненные санкции автоматически не отменяются. Если редакция впервые пересекает порог, действует обычное правило. Если оценка после санкции упала ниже порога, уходит карточка админу.

Реплики: набор в файле данных `data-static/jokes.json`, выбор через переданный источник случайности. Исполнитель кладёт 10 заготовок; итоговые тексты заменяет лид, формат файла менять нельзя.

### 3.6.0 Спам судится по контексту и по автору (решение владельца 29.09)

Основание: на чате владельца 58 из 58 карточек старых правил оказались ложными; все - сообщения участников с историей в чате. Прогон `.scratch/work/v1/calib2`.

- В `state` добавлено поле `sender_history`: для первого сообщения участника `first message of this sender in the chat`, иначе `member of the chat, <N> earlier messages over <D> days`. N и D считаются по сообщениям участника в этом чате, включая импортированные.
- `previous_messages`: 8 последних реплик вместо 3 (настройка прежняя, значение по умолчанию 8).
- Четыре вопроса о спаме в `eval/questions.json` заменены формулировками, которые судят сообщение по `replied_to`, `previous_messages` и `sender_history`. Имена и типы вопросов прежние. Файл с новыми формулировками даёт лид.
- Правила 3, 4 и 5 раздела 3.6 (парилка, удаление, карточка по оценке текста) применяются только к новичку. Новичок - участник, у которого сообщений в этом чате, включая импортированные и текущее, не больше `spam_newcomer_messages` (по умолчанию 5; 0 отключает ограничение, и правила действуют на всех). К остальным участникам оценка спама по тексту не применяется: ни санкций, ни карточек. Оценка в базу пишется как раньше.
- Новичком считается только тот, чей вход в чат бот видел сам (`members.joined_seen_at`: обновление о вступлении или служебное сообщение о новых участниках). Кто был в чате до бота, по тексту не судится, сколько бы сообщений у него ни было в базе.
- Молчун судится как новичок, но только по тексту. Молчун - участник, чьего входа бот не видел и которого не знает загруженная история: его запись появилась после завершённого импорта истории этого чата (решение владельца 05.10). Первые `spam_newcomer_messages` сообщений молчуна проходят правила парилки и карточки по оценке текста; правило о рекламном профиле к нему не применяется. Пока история чата не загружена, молчунов нет: бот не может отличить спящий аккаунт от давнего участника.
- Как считается число сообщений: для нового сообщения - сообщения автора, отправленные не позже него (позиция на момент отправки; задержанная оценка и сообщения, пришедшие следом, результат не меняют); для правки сообщения - все сообщения автора на момент правки.
- Правило о рекламном профиле применяется только к новичку по этому же счёту. Участник с историей, включая импортированную, по профилю не судится.
- Сообщения не от людей не судятся и целью `/spam`, `/report` и кнопок не становятся: автоматическая пересылка из привязанного канала (`is_automatic_forward`, отправитель 777000), сообщения от имени чата или канала (`sender_chat`), служебные сообщения (создание темы форума и прочие). В форуме ответ на служебное сообщение о создании темы считается сообщением без ответа.
- Правило 2 (участник с высокой кармой) для не новичка карточку не создаёт.
- Испытательный срок после разбана и правило о рекламном профиле работают как раньше.
- Уже открытые карточки по сообщениям не новичков миграция закрывает с решением `not_newcomer`.

Команда админа `/spam` (решение владельца 29.09): админ чата отвечает командой `/spam` на сообщение.
- Право: свежий `getChatMember` отправителя команды, статус `creator` или `administrator`. Не админу команда не выполняется, команда удаляется, ответа в чат нет.
- Действие: команда удаляется; сообщение удаляется; автор отправляется в парилку по шагам раздела 3.6 (ограничение, запись бани с категорией `admin`, шуточная реплика с кнопкой); текст сообщения сохраняется по правилам хранения спама.
- Режим наблюдения команду не блокирует: это решение человека.
- Цель - админ, владелец или бот: действие не выполняется, команда удаляется, админу-отправителю уходит личное сообщение с причиной.
- Команда без ответа на сообщение: удаляется, ничего не происходит.
- Повторная команда на то же сообщение второй раз ничего не делает.
- Защита высокой кармы на команду админа не действует.

### 3.6.4 Каналы как участники (решение владельца 01.10)

Человек может писать в группе от имени своего канала. Telegram не сообщает, кто за каналом стоит, поэтому участником считается сам канал.

- Автор-канал: сообщение с `sender_chat`, у которого идентификатор отличается от идентификатора самой группы, и без признака `is_automatic_forward`. Автоматическая пересылка поста привязанного канала и сообщения анонимного админа (от имени самой группы) по-прежнему не судятся и в карму не идут.
- Канал хранится как участник с отрицательным идентификатором `sender_chat.id`, названием канала как именем, `username` канала и признаком `is_channel`. Схема меняется новой миграцией.
- Карма канала считается по тем же правилам, что у человека: оценка Jev, лестница сигналов, реакции на его сообщения, серия, убывание. Реакции, поставленные от имени канала, считаются как раньше.
- Тег каналу не ставится (Telegram не позволяет), наказания за низкую карму к каналу не применяются.
- Спам: канал, впервые увиденный ботом в живом сообщении, считается новичком первые `spam_newcomer_messages` сообщений; канал, у которого есть импортированные сообщения, новичком не считается. В первые 7 суток после подключения чата любой впервые встреченный канал считается старым: до загрузки истории бот не может отличить давнего автора от нового. Правило о рекламном профиле к каналам не применяется. При оценке не ниже `spam_auto_threshold`: сообщение удаляется, канал банится в группе (`banChatSenderChat`), создаётся запись бани с замаскированным названием, в чат уходит реплика без кнопки разбана, админам уходит карточка «Удалил спам и забанил канал» с кнопкой «Не спам, вернуть». «Не спам, вернуть» снимает бан (`unbanChatSenderChat`), удаляет запись бани и возвращает текст. От `spam_review_threshold` до порога - карточка с кнопками «Спам» и «Не спам». Разбан через Mini App каналу недоступен.
- `/spam` и `/report` на сообщение канала работают: `/spam` удаляет сообщение и банит канал; проверка «цель - админ» к каналу не применяется.
- Отказы `banChatSenderChat` и `unbanChatSenderChat` - по общему правилу сохраняемых операций.
- Импорт: сообщения с `from_id` вида `channel<id>` импортируются как сообщения канала с идентификатором `-100<id>`; повторная загрузка файла добавляет только то, чего ещё нет.
- Mini App: канал стоит в общем лидерборде с пометкой «канал» (поле `is_channel` в строке лидерборда и на странице участника), у канала есть страница как у человека. Вкладка «Я» для человека не меняется.

### 3.6.2 Автоудаление, кнопки админа и ответ бота (решение владельца 29.09)

Основание: живой случай 29.09, сообщение новичка с оценкой 0.98. Админ нажал «Забанить»: участник забанен, сообщение осталось в чате, бот админу ничего не написал.

Автоудаление:
- `spam_auto_threshold` по умолчанию 0.60 (решение владельца 29.10). Новичок (раздел 3.6.0) с оценкой спама не ниже порога: сообщение удаляется, автор отправляется в парилку по шагам раздела 3.6, админам уходит карточка «Удалил спам» с цитатой по разделу 3.6.1.
- Режим наблюдения это правило, команду `/spam` и кнопки админа не блокирует. Остальное в режиме наблюдения по-прежнему только показывается.
- Новичок с оценкой от `spam_review_threshold` до порога автоудаления: сообщение остаётся, админам уходит карточка. Правило 4 раздела 3.6 (удаление с карточкой от 0.50) отменено; настройка `spam_review_delete_threshold` остаётся в схеме и не используется.

Решение владельца 31.10.2026: в AI Masters Me 🧬 Антицыганский чат порог автоудаления 0.46, карточки от 0.45; запись штатным `changeSetting` с версией и аудитом. Другие чаты и значения порогов сохраняются. Служебный `spam_review_delete_threshold` (0.60 в AI Masters) остаётся в схеме и истории; устаревшая связь `spam_review_delete_threshold ≤ spam_auto_threshold` удалена по подтверждению 31.10, действуют остальные инварианты раздела 3.9.

Кнопки карточки о спаме:
- пока сообщение в чате: «Спам» и «Не спам»;
- после удаления: «Не спам, вернуть» и «Забанить».
- «Спам»: сообщение удаляется, автор отправляется в парилку, как при автоудалении.
- «Забанить»: сообщение удаляется, если оно ещё в чате; участник банится.
- «Не спам» (сообщение в чате): карточка закрывается, санкций нет.
- «Не спам, вернуть»: ограничение или бан снимается, запись бани удаляется, текст сообщения публикуется в чат от имени бота строкой `<имя автора>: <текст>`, испытательный срок не назначается. Для сообщения с вложением возвращается подпись и пометка о вложении.
- Кнопка «Разбанить» на карточках о спаме заменена кнопкой «Не спам, вернуть».

Ответ бота админу после каждого нажатия:
- всплывающий ответ на `callback_query` с итогом одной фразой;
- сообщение карточки правится (`editMessageText`): к тексту добавляется строка `Решение: <что сделано>. <имя админа>, <дата и время в часовом поясе чата>`, кнопки заменяются на оставшиеся допустимые действия;
- итог перечисляет выполненное и невыполненное, например «сообщение удалено, участник забанен» или «участник забанен; сообщение удалить не смог: <причина>»;
- правка карточки выполняется у всех админов, получивших её;
- отказ `editMessageText` решения не отменяет; итог остаётся во всплывающем ответе и на экране админа.
- После команды `/spam` админу-отправителю уходит личное сообщение с тем же итогом и кнопкой «Не спам, вернуть».

### 3.6.3 Язык карточек и режим наблюдения (решение владельца 29.09)

Владелец получил карточку «Режим наблюдения: сделал бы» и не понял, что произошло и что от него нужно.

- Карточек вида «сделал бы» больше нет. Карточка говорит только о том, что бот сделал, или просит решения.
- Режим наблюдения спам не затрагивает (раздел 3.6.2). В режиме наблюдения остаются только наказания за низкую карму раздела 3.7: они не применяются и карточек админам не создают; что было бы применено, видно на экране админа.
- Заголовок карточки - обычная фраза: «Удалил спам и заглушил автора», «Похоже на спам, реши», «Жалоба на сообщение», «Не смог удалить сообщение».
- Оценка пишется процентом: «Уверенность: 98%».
- Порядок строк: заголовок; участник; категория; уверенность; цитата; ссылка.
- Цитата сообщения оформляется как цитата Telegram: сущность `blockquote` в `entities` с длиной в единицах UTF-16. `parse_mode` не используется, текст участника разметкой не становится.
- Слова «режим наблюдения», имена вопросов и служебные коды в карточках не используются.

### 3.6.1 Карточка админу

Решение владельца 29.09: админ принимает решение по карточке, только видя само сообщение.

Каждая карточка о сообщении (спам, «сделал бы», проверка, жалоба, сбой удаления) содержит:
- имя участника и, если есть, `@username`;
- цитату сообщения: до 500 графемных кластеров, с пометкой об усечении; для сообщения без текста - вид вложения и подпись;
- ссылку на сообщение: `https://t.me/<username чата>/<message_id>` для чата с именем, `https://t.me/c/<идентификатор без префикса -100>/<message_id>` для чата без имени; ссылка даётся и текстом, и URL-кнопкой «Открыть сообщение»;
- категорию словами на русском (например «заработок и крипта», «заманивание в канал»), а не именем вопроса;
- оценку спама и то, что бот сделал или сделал бы.

Текст сообщения, по которому создана карточка, сохраняется по правилу хранения удалённого спама (раздел 3.10): доступен только свежепроверенному админу чата, удаляется не позднее 30 суток, в том числе из копий в операциях. Если текста на момент создания карточки уже нет, карточка говорит об этом прямо и даёт ссылку.

Текст участника в карточке - данные: разметка не применяется, длина ограничена лимитом сообщения Telegram.

### 3.6.6 Стоп-слово Polzastas (решение владельца 04.10)

- Упоминание: `polzastas` в любом регистре в тексте или подписи сообщения (в том числе `@polzastas`, `t.me/polzastas`) или в адресе скрытой ссылки (`text_link`). Русское написание, имя и профиль автора не проверяются.
- Действует на любого участника, у которого сообщений в этом чате, включая импортированные и текущее, не больше `spam_newcomer_messages`, видел бот его вход или нет (решение владельца 04.10: спамер, чей вход бот не видел, под правило новичка не попадал), и на участника на испытательном сроке. Остальных не трогает.

### 3.6.8 Вход по заявке: лягушонок на двери (решение владельца 24.11)

Зачем: спамер входит тихо и пишет через минуты или недели (за 30 дней до 24.11: 161 автопарилка на 519 входов, 57 % спамеров ждали больше часа, самый долгий 35 дней). Пока он внутри, он видит участников. Дверь закрывается до входа.

- Настройка чата `join_gate` (по умолчанию выключена) и `join_gate_minutes` (по умолчанию 10, от 2 до 60). В группе включены заявки на вступление, бот - админ с правом приглашать; по возможности бот назначен стражем заявок (Bot API 10.1, `guard_bot`).
- Заявка со стражем (`chat_join_request` с `query_id`): бот за 10 секунд показывает окно Mini App `sendChatJoinRequestWebApp`. Без стража или когда окно показать не удалось: бот пишет в личку по `user_chat_id` (5 минут с заявки) кнопкой `web_app` с тем же окном. Не удалась и личка: заявка остаётся админам (`queue` у стража, без ответа без него). Окно, которое никто не открыл (процесс встал между записью заявки и вызовом), через 15 секунд открывает тик бота: личкой, пока не прошли 5 минут, иначе заявка остаётся админам.
- Окно: лягушонок Жевчика и шутка, шесть пиксельных зверей в случайном порядке и с случайным отражением, ровно один - лягушонок. Тык в лягушонка - заявка одобрена. Мимо - звери перемешиваются, вторая попытка; второй промах - отказ. Нажатие несёт номер раскладки (0 или 1): нажатие на прежней раскладке (второе открытое окно) попытку не тратит, сервер отдаёт текущую. Нет ответа за `join_gate_minutes` - отказ; срок действует и при нажатии, не только при проходе тика. Отказ по молчанию - только когда окно точно открылось; окно, которое не открылось или открытие оборвалось, оставляет заявку админам. Отказ без бана: заявку можно подать снова, но не больше трёх проверок на человека в чате за сутки (считаются выданные окна, отказы по лимиту не считаются); четвёртая заявка за сутки отклоняется без окна, стражу - сразу в обработке заявки.
- Решение одно на проверку: нажатие, срок и вход, одобренный админом руками, меняют `pending` одним условным `UPDATE`, кто первый. Ответ в Telegram отправляет тот, кто захватил отправку (аренда 30 секунд); сбой сети и 5xx повторяются по нарастающей паузе до 8 раз; «заявки уже нет» и «уже участник» - отправка закрыта. Для стража сначала `answerChatJoinRequestQuery`, при отказе Telegram по `query_id` - `approveChatJoinRequest` / `declineChatJoinRequest`. Эти два метода адресуются парой чат/человек, то есть текущей заявке: новая заявка того же человека снимает неотправленный ответ старой проверки (`skipped`), а вызов по паре идёт под блокировкой пары и только пока новее заявки нет. Окно пишет «Пустил» только после того, как Telegram принял одобрение; пока ответ в пути - «Открываю дверь…», окончательный отказ Telegram - «заявка у админов».
- Выключенный `join_gate`: заявка со стражем сразу уходит админам (`queue`), без стража бот её не трогает.
- Прошедший дверь остаётся новичком по разделу 3.6.0: первые сообщения судятся как раньше. Вошедший мимо заявки (старая ссылка-приглашение без заявки) встречает обычный антиспам.
- Кнопка «Разбанить меня» (раздел 3.6) срабатывает только после той же проверки с лягушонком в Mini App. Две попытки на проверку; проваленная проверка кнопку не сжигает, новая - не раньше чем через 10 минут.
- Монитор (раздел 3.13) пишет строку «Вход: пустил N, отказ M (промах A, молчал B, лимит C)»; «пустил» - одобрение, принятое Telegram.
- Окно, звери и тексты - без названий зверей в разметке и в ответе API: клиент получает только пиксели.

### 3.6.5 Админ наказывает из Mini App (решение владельца 01.10)

Управлять может любой админ чата, в который добавлен бот. Роль проверяется свежим `getChatMember` на каждый запрос.

- Где кнопки: на странице участника (открывается из лидерборда или из поиска во вкладке «Админ») блок «Модерация»; в «Бане» у каждой записи - настоящее имя, наказание словами и кнопка снятия. Участник без роли админа этих блоков не видит, сервер отвечает ему 403.
- «В парилку»: открывает три срока - «1 час», «Сутки», «Неделя». Нажатие срока ограничивает участника до этого времени (`restrictChatMember` с `until_date`). По истечении срока Telegram сам снимает ограничение, запись в бане удаляется, бана не будет.
- «Забанить»: первое нажатие спрашивает «Точно забанить?», второе банит (`banChatMember`). Прошлые сообщения участника остаются: `banChatMember` в супергруппе закрывает забаненному доступ к истории, сообщения для остальных не удаляет. Канал можно только забанить.
- «Выпустить из парилки» / «Разбанить»: снимает ограничение или бан, удаляет запись в бане и реплику бота о наказании. В чат ничего не пишется. Забаненному нужно зайти в чат заново самому. Так же снимается наказание, которое бот дал сам.
- Карма наказанного не меняется. Забаненный (любым способом) не стоит в лидерборде, пока бан не снят.
- В чат бот пишет жёсткую реплику из набора для решений админа (`admin_steam`, `admin_ban` в `data-static/jokes.json`) с кнопкой «Попросить разбан». Каналу реплика не пишется.
- Остальным админам в личку ничего не приходит. Каждое действие, дошедшее до Telegram, и неудачное тоже, пишется в «Журнал наказаний» во вкладке «Админ»: кто, что, когда, чем кончилось. Отказ до обращения к Telegram (себя, неверный срок, уже забанен, наказания нет, идёт предыдущее действие) в журнал не пишется: админ видит его сразу на экране.
- Админа чата и владельца наказать нельзя: ответ «Не вышло: это админ чата». Себя наказать нельзя. Если у бота нет права: «Не вышло: у бота нет права банить участников».
- Наказанный админом сам выйти не может: проверка объяснения моделью к нему не применяется. Во вкладке «Разбан» он видит «Вы в парилке до …» или «Вы забанены», пояснение, что это решение админа, и кнопку «Попросить разбан». Просьба одна на наказание. Админам приходит карточка «Участник просит разбан» с кнопками «Разбанить» и «Оставить». «Разбанить» снимает наказание без испытательного срока. «Оставить» - участник видит «Админы оставили наказание в силе». «Разбанить» на карточке тоже удаляет реплику бота. Карточка относится к одному наказанию: когда его заменили, сняли или срок вышел, карточка закрывается и её кнопки отвечают «Кнопка устарела».
- Режим наблюдения на действия админа не влияет.

### 3.7 Наказания, привилегии, жалоба

Решение лида: состав возможностей в `DESIGN.md` не задан.

Наказания применяются в момент, когда карма пересекает порог сверху вниз. Повторное применение - только после нового пересечения.

| Порог | Действие | Вызов Telegram | Выход |
|---|---|---|---|
| карма ≤ -10 | запрет ссылок, медиа и стикеров; минусующие реакции участника не учитываются | `restrictChatMember`: текст разрешён, остальное запрещено | карма > -10: права возвращаются к правам чата по умолчанию |
| карма ≤ -25 | мьют на 24 часа | `restrictChatMember` с `until_date` | срок истёк: действует строка -10 |
| карма ≤ -40 | мьют на 7 суток | `restrictChatMember` с `until_date` | срок истёк: действует строка -10 |

Наказание за карму записи в бане не создаёт. Админы и владелец чата наказаниям не подлежат. В режиме наблюдения наказания не применяются.

Привилегии при карме ≥ `protect_threshold`:

| Привилегия | Изменение алгоритма | Наблюдаемый результат |
|---|---|---|
| Мягкая проверка | действует правило 2 раздела 3.6 | сообщение со ссылкой и `spam` 0.6 остаётся в чате, админам уходит карточка |
| Защита от бана | правило 2 проверяется до правил 3 и 4 и перехватывает оценку текста и оценку профиля; для защищённого участника правила 3 и 4 недостижимы | вызовов `restrictChatMember`, `banChatMember`, `deleteMessage` нет |
| Вес голоса | `voter_weight` из раздела 3.4, действует для всех | реакция участника с кармой 100 даёт больше, чем с кармой 0 |

Жалоба: команда `/report` ответом на сообщение. Команда удаляется из чата.
- Заявитель с кармой ≥ `protect_threshold`: сообщение удаляется, его текст сохраняется по правилам хранения спама, админам уходит карточка с кнопками «подтвердить» и «вернуть». «Вернуть» публикует текст от имени бота с именем автора.
- Остальные заявители: админам уходит карточка, сообщение остаётся.
- Повторная жалоба на то же сообщение не создаёт второй карточки.
- Жалоба на сообщение админа или бота отклоняется.
- «Подтвердить» начисляет по таблице 3.4; награду получает первый заявитель.

Знак «похоже на спам» (решение владельца 07.10): реакция `report_reaction_emoji` (по умолчанию 🖕; пустое значение выключает знак) на сообщение участника. Автор, который сейчас судится по тексту (раздел 3.6.0; сообщения считаются на момент жалобы, а не до отмеченного), с кармой ниже `report_steam_karma` (по умолчанию 5) сразу уходит в парилку: сообщение удаляется, админам приходит обычная карточка парилки (решение владельца 29.10). Иначе сообщение не трогается, карма не меняется, бот ничего не ставит и не пишет: админам уходит карточка «Участник пожаловался: похоже на спам, реши» с цитатой, ссылкой и кнопками «Спам» (удалить сообщение, автора в парилку) и «Не спам», как у карточки от модели. Одна карточка на сообщение; реакция бота, от имени чата, самого автора или снятая знаком не считается; на одного участника действует лимит `report_daily_limit` в сутки, парилка по знаку тоже считается. Это не `/report`: право дозора и начисления за жалобу к знаку не относятся.

### 3.8 Mini App: запуск и доступ

- В группах используется `InlineKeyboardButton.url` со ссылкой `https://t.me/<bot_username>?startapp=<context>`. Поле `web_app` в группах не используется.
- `<context>` содержит `chat_id` и назначение экрана. Сервер берёт его только из `start_param` внутри подписанного `initData`.
- Проверка `initData`: исходная строка разбирается на пары, `hash` исключается, пары сортируются по ключу и соединяются `\n`. `secret_key = HMAC_SHA256(key="WebAppData", message=bot_token)`. Ожидаемый хэш `hex(HMAC_SHA256(key=secret_key, message=data_check_string))` сравнивается за постоянное время. Затем `auth_date` не старше 24 часов.
- Лидерборд, личные страницы и баня открыты любому, кто прошёл проверку `initData`. Членство в чате не требуется.
- Экран админа и каждое его действие требуют свежего `getChatMember` со статусом `creator` или `administrator`. Положительный результат не кэшируется.

### 3.9 Экраны

Лидерборд: место, имя, карма за период; периоды неделя, месяц, всё время. Боты в лидерборд не входят ни за один период, пока выключена настройка `bots_in_rating` (по умолчанию выключена; решение владельца 01.10). Во вкладке «Админ» это галочка «Боты в рейтинге». Включена: боты стоят в лидерборде с пометкой «бот» и получают тег с кармой по разделу 3.12. Выключена: ботов в лидерборде нет, тег с кармой, который бот ставил ботам раньше, снимается. Экспорт истории не сообщает, кто бот, поэтому бот распознаётся по ответу Telegram (`getChatMember`, поле `is_bot`) при первой постановке тега: участник помечается ботом; тег ему ставится только при включённой настройке. Ограничение: при `karma_tag_enabled = false` тегов нет, значит и бот из импорта не распознаётся.

Личная страница:
- сообщения: пять последних, самые заплюсованные, с наибольшим числом ответов; у каждого отрывок и ссылка на оригинал;
- цифры: карма, место, изменение за неделю, график кармы по времени, число благодарностей, число ответов на вопросы, число пойманных спамеров, серия активных недель;
- предупреждение об убывании, если до его начала меньше 3 суток.

`caught_spammers_count` - число уникальных участников, по сообщениям которых жалоба этого пользователя подтверждена админом; повторные подтверждения по одному участнику единицу не добавляют.

Баня: замаскированное имя, категория, объяснение из набора, картинка, дата. Маска имени - чистая функция с литеральными примерами в тестах: первый графемный кластер и три звёздочки. Публичный идентификатор записи непрозрачный.

Разбан: кнопка «Разбанить меня» и результат.

Вкладки (решение владельца 29.09): «Разбан» видна только участнику с записью в бане, «Админ» - только админу чата (свежий `getChatMember` при открытии; отказ проверки прячет вкладку). Ссылка на скрытый экран открывает лидерборд. Защита экрана админа на сервере не меняется.

Реплики бота (решение владельца 29.09): жёсткий юмор в духе стендапа, мат разрешён; объект шутки - спамер и спам.

Экран админа: настройки чата с проверкой по схеме, журнал изменений, загрузка файла импорта, продление наблюдения.

Схема настроек - машиночитаемый файл и исчерпывающий перечень разрешённых ключей. Для каждого ключа: `name`, `type`, `default`, `nullable`, `minimum`, `maximum`, `enum` или схема элементов для составного значения, взаимные инварианты. Менять настройки может только свежепроверенный админ этого чата. Новая версия не меняет уже созданные операции и действует на операции, созданные после её записи. Общие правила: пороги в [0, 1]; `spam_review_threshold ≤ spam_review_delete_threshold` и `spam_review_threshold ≤ spam_auto_threshold`; веса в [-100, 100]; сроки больше 0 и не больше 366 суток; неизвестный ключ отклоняется. Конфликт версий: изменение несёт номер версии, на которой основано.

### 3.10 Хранение

- Бессрочно: оценки Jev, счётчики, ссылка на сообщение.
- Полный текст обычного сообщения в базу не пишется. Задание оценки хранит текст до завершения оценки и не дольше 24 часов.
- Отрывок до 200 графемных кластеров (`Intl.Segmenter`) живёт 7 суток, затем остаётся только у лучших сообщений.
- Лучшие сообщения: не больше 10 на участника в чате, порядок `(положительная карма сообщения DESC, число ответов DESC, message_id DESC)`. Решение лида.
- Текст удалённого спама и сообщений, убранных жалобой, доступен только свежепроверенному админу чата и удаляется не позднее 30 суток. Очистка после простоя догоняет пропущенное.
- Файл импорта удаляется после подсчёта и при любой ошибке.

### 3.11 Импорт истории

Формат - JSON экспорта Telegram Desktop. Импорт доверяет файлу, загруженному действующим админом. Сравнение идентификатора чата защищает от ошибки и происхождение файла не доказывает; экран показывает это перед подтверждением. Лимит файла 50 МБ. Сообщения оцениваются Jev теми же вопросами. Реакции учитываются как счётчик, без `pair_factor` и `voter_weight`. Задание импорта хранится в базе и продолжается после перезапуска.

### 3.12 Тег с кармой

Решение владельца: рядом с именем участника видно его карму числом. Теги-звания не используются.

- Вызов: `setChatMemberTag(chat_id, user_id, tag)`. Тег 0-16 знаков, эмодзи запрещены. Работает только для обычных участников; боту нужно право `can_manage_tags`.
- Текст тега: шаблон из настройки `karma_tag_template`, по умолчанию `{n}` (решение владельца: вид `+321`), где `{n}` - карма, округлённая до целого (`Math.round`), со знаком: `+321` для положительной, `-12` для отрицательной, `0` для нуля. Шаблон проверяется схемой: содержит `{n}`, без эмодзи, результат для числа из 6 знаков не длиннее 16.
- Настройка `karma_tag_enabled`, по умолчанию `true`.
- Тег ставится участнику, у которого есть хотя бы одно событие кармы. Участнику с кармой 0 без событий тег не ставится.
- Обновление: когда целое значение кармы участника отличается от последнего установленного. Последний установленный текст хранится в базе; совпадающий текст повторно не отправляется.
- Частота: не чаще одного обновления тега на участника в 10 минут (настройка `karma_tag_min_interval_minutes`); отложенное обновление берёт карму на момент отправки. Общий темп вызовов тегов на чат не больше 20 в минуту.
- Вызов выполняется как сохраняемая операция по общему правилу раздела 4, вид операции `set_tag`.
- Админы, владелец чата и боты: вызова нет. Роль берётся из ответа Telegram; ответ «участник - администратор» или «нельзя изменить» завершает операцию без повтора и без карточки, участник помечается как не подлежащий тегу до смены роли.
- Режим наблюдения теги не отключает: тег не санкция.
- Первичная расстановка после импорта или включения настройки идёт той же очередью с тем же темпом.
- При `karma_tag_enabled = false` новые теги не ставятся, уже поставленные не снимаются.
- Изменение схемы базы только новой миграцией.

### 3.13 Ежедневный монитор (решение владельца 29.10)

- `node dist/main.js monitor` (`src/monitor.ts`) только читает базу и печатает отчёт за последние 24 часа по каждому чату: что бот сделал сам (парилка, удаление без парилки, бан после парилки), что админы сделали руками (кнопки «Спам» и «Забанить» на карточке, `/spam`, наказание из Mini App), что отменили как ложное («Не спам», «Не спам, вернуть», разбан с карточки или из Mini App, разбан кнопкой самим участником), карточки «реши» без решения и отказы Telegram при удалении, заглушении и бане.
- Предложения: порог автоудаления, при котором бот за 14 дней сам убрал бы не меньше двух удалённых руками сообщений, а все сообщения с решением «не спам» остались бы ниже, и не ниже порога карточек; удалённые руками тексты, которые фразы 3.6.7 не узнали; фразы, сработавшие на сообщение с решением «не спам».
- Первая строка - светофор: 🔴 бот не смог удалить, заглушить или забанить либо оценки Jev висят больше часа; 🟡 была ручная работа, ложные или висящие карточки; 🟢 иначе.
- Отчёт содержит текст удалённого спама и уходит владельцу через pi (исключение из 3.10 по решению владельца 29.10). Запуск раз в сутки на сервере, доставка - `ops/monitor/README.md`.

## 4. Таблица отказов

Общее правило внешних вызовов: 429 повторяется по `retry_after`. Сеть и 5xx повторяются до трёх попыток с растущей паузой. 400 и 403 не повторяются. Исчерпанный отказ пишется в журнал структурированно, без токенов и без полного текста обычного сообщения.

Каждый обязательный внешний вызов, меняющий состояние Telegram, выполняется как сохраняемая операция с полями `operation_id`, `operation_kind`, `idempotency_key`, `status`, `attempt_count`, `next_attempt_at`, `last_error_code`, `last_error_at`. Статусы: `pending`, `running`, `completed`, `failed`, `outcome_unknown`. После исчерпания повторов шаг выполненным не считается: операция получает `failed` и видна на экране админа. Если запрос мог быть принят Telegram, а ответ потерян, операция получает `outcome_unknown` и автоматически не повторяется, когда повтор может создать видимый дубль.

## 6. Тесты

- Самый высокий шов: обновление Telegram на входе, записанные вызовы Telegram и состояние базы на выходе.
- Обязательны все тесты из колонки «Тест» и тест на каждую строку F2 - F24.
- Тесты на проводе для Jev и модели описания: уходящий запрос сверяется с литералом целиком.
- PBT: формулы кармы, маска имени, обрезка отрывка, перестановка пар `initData`.
- Проверка `initData`: фиксированные векторы, посчитанные независимо от проверяемого кода (значения в тесте литералами), и мутации каждого подписанного поля, порядка, `hash`, `auth_date`.
- Мутанты, которые обязаны краснеть: порог спама, знак начисления минусующей реакции, проверка подписи `initData`, проверка прав админа, сравнение идентификатора чата при импорте.
- Команда `npm run test:coverage` пишет lcov в `$QG_LCOV`.

## 7. Модель TLA+

Порядок шагов парилки, бана и разбана обеспечивается сохраняемым автоматом состояний из раздела 3.6; каждый переход проверяется тестами отказа до и после внешнего вызова и записи в базу.

Вход по заявке (раздел 3.6.8) - `specs/tla/Gate.tla`: решение одно (`OneDecision`), отправленное совпадает с решением (`SentMatches`), успешный вызов бота один (`OneCall`), закрытая отправка не оставляет заявку открытой (`NoHanging`), решение старой проверки не попадает в новую заявку того же человека (`NoStray`). Мутанты, которые обязаны краснеть: без условия `pending` (`SentMatches`), без запасного вызова по заявке (`NoHanging`), без проверки новой заявки перед вызовом по паре (`NoStray`). Вне модели: лимит трёх проверок, срок при нажатии, окно, которое не открылось; их держат тесты `tests/gate.test.ts`.

Разбан по кнопке против бана по сроку и действия админа - `specs/tla/Appeal.tla`, проверка `specs/tla/check.sh`. Инварианты: кнопка срабатывает один раз (`OneAppeal`); бан в Telegram всегда виден записью бани (`NoHiddenBan`); наказание админа кнопка не снимает (`AdminWins`); нажал и админ не вмешался - в конце участник свободен (`ClickFrees`). Мутанты, которые обязаны краснеть: без ожидания чужих потоков (`NoHiddenBan`), без проверки источника записи (`AdminWins`), без проверки «ещё не нажимал» (`OneAppeal`). Тесты соответствия: `T-appeal-ban-in-flight` (tests/r3-sanctions.test.ts), `model Appeal, AdminWins` (tests/admin-moderation.test.ts).
